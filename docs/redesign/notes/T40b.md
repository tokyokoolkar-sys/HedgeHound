Branch `T40b` (worktree `../hh-T40b`), from main `61f5b96`. Not merged.

## What changed

### `src/lib/scan/`
- **`query.ts` (new, pure, node-testable):** `scanKey`, `scanQueryString`, `refetchIntervalMs`, `staleTimeMs`, `nextMisses`, `isStale`, and the constants `SCAN_REFETCH_MS` (30 s), `SCAN_STALE_MS` (25 s), `BACKOFF_STEPS_MS` (30 s, 2 min, 5 min), `STALE_AFTER_MS` (300 s). `use-scan.ts` re-exports the constants it used to define.
- **`types.ts`:** `ScanParams` gains `cost`. `DEFAULT_SCAN_PARAMS` is `{min 1, hold 72, cost DEFAULT_BOOK.cost (0.30), lev 2}`, imported from `scent.ts`, so there is one source for the number. `ScanResult` gains optional `misses` (consecutive fallback answers).
- **`api.ts`:** builds the URL with `scanQueryString`, so the request is `/api/scan?min=1&hold=72&cost=0.3&lev=2`. The server's own default is 0.2, so before this change live nets used 0.2 and sample nets 0.3.
- **`use-scan.ts`:**
  - Query key is `["scan", {min, hold, cost, lev}]`.
  - `refetchInterval` and `staleTime` are functions of the last answer (`q.state.data`), as TanStack Query expects. The `queryFn` stamps `misses` on each result from the previous cached result: `0` after a live answer, `+1` after a fallback.
  - Interval: no answer yet or live gives 30 s. Fallback with misses 1 gives 30 s, 2 gives 2 min, 3 or more gives 5 min.
  - `staleTime` while offline equals the same backoff step, so window focus and remount cannot trigger an extra failing request inside a step. It is 25 s while live.
  - New return field `stale: boolean`: `live && now - ts > 300 s`, where `now` is the existing client-only clock state. It is `null` on the server and before mount, so `stale` is always false in SSR and in the first client render (no hydration mismatch).
- **`adapter.test.ts`:** +12 tests (cost default, URL and key, sample at the same cost, backoff steps and reset, 3-minute request count, staleTime, `isStale`). I put them in this file rather than a new `query.test.ts` because a new file needs a `package.json` test-script edit, which the ticket does not list.

## Open issues and proposals (not applied)
1. **STALE flickers at 300 s.** The scanner polls every 300 s plus the poll's own duration, and we pick up the new `ts` within 30 s. So a healthy scanner will be shown STALE for up to about 30 s plus the poll time at the end of every cycle (roughly 10% of the time). The ticket says 300 s, so I implemented that; `STALE_AFTER_MS` is one constant. Proposal: 360 s (one poll plus a grace) and update the SourceTag tooltip, or keep 300 s and accept the flicker.
2. **Den footer still carries the yield claim.** `den-desk.tsx:577`: "At this size the honest outcome of a working spread is a few dollars a year, plus whatever you learned, plus maybe a points program." Same claim as the hero line I reworded, but not named in the ticket. Proposed text: "At this size this is a classroom, not a paycheck. No figure on this page is a forecast, and a points program, if there is one, is a footnote." Apply if you agree.
3. **Other typed-in numbers in copy:** the hero `CLOUD` words ("0.30% round trip", "144 samples", "$250k volume", "$50k open interest") are policy constants, not readings. They could read from `DEFAULT_BOOK`, `MIN_VOL` and `MIN_OI` so they cannot drift. Not touched.
4. **`sampleScan()` always uses `DEFAULT_BOOK`,** so if a caller passes a `cost` other than 0.30, the fallback is still computed at 0.30. Fine today (nobody passes one). If a cost slider ever feeds the query, `sampleScan` needs the same params.
5. **Backoff covers any fallback,** including a scanner that is up but reports `err` or has `ts` 0 (no network error there, only a slower retry). After a scanner restart it can take up to 30 s to see the first live poll; this was visible in the live run.
6. **First LIVE tag:** when T20+ render it, re-check `stale` in place; I could only exercise it through a temporary probe.
